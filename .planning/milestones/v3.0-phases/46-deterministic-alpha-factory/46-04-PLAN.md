<open_question_resolutions>
- **O1 (complexity limits):** `max_depth`/`max_nodes` are part of the grammar fingerprint (46-01) and enforced as a complexity budget by `validate_candidate` (46-03); the budget guard here also reads them as a structural memory bound (bounded AST depth/node count + bounded population frontier, no unbounded accumulation).
- **O2 (resume):** replay-based resume — `drive_alpha_generation` re-derives the frontier from seed+step on restart (checkpoint is a recovery optimization; this plan may persist a coarse frontier checkpoint but never relies on serialized PRNG state for correctness).
- **O3 (seed-pool order):** frozen by plan 46-02; this plan does not alter it.
- **O4 (low_coverage):** NOT assigned in Phase 46. Valid novel candidates get the new `generated` status (the "pending/unevaluated state" O4 recommends); `low_coverage`/`admitted`/`rejected`/`failed` remain Phase 47's. Adding `generated` is a deliberate planner decision: the candidate ledger is append-only with an immutable status (UPDATE trigger aborts), so a generated valid candidate needs a permanent generation-outcome status distinct from every evaluation/failure status in the existing CHECK.
</open_question_resolutions>

## Trust Boundaries

| Boundary | Description |
|---|---|
| Untrusted worker → service | Append/progress/transition callbacks cross in with only a server token + version. |
| Generation loop → append-only ledger | Candidate/lineage facts cross into durable storage. |
| Budget state → terminal transition | Budget exhaustion requests a lifecycle transition. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-46-10 | Elevation | worker append/progress callbacks | high | mitigate | `append_candidate` / `append_candidate_lineage` in the adapter call `service._validate_attempt_token` first and fail closed on a stale/invalid token or version (D-10, T-45-08). |
| T-46-11 | Denial of service | unbounded generation | high | mitigate | `BudgetGuard` checks candidate/expression/wall-clock budgets at the top of each step before generating; exhaustion is a normal `completed` terminal, never unbounded (research Pitfall 4). |
| T-46-12 | Tampering/Repudiation | candidate ordering & replay | high | mitigate | Single-threaded step order with `attempt_ordinal = step + 1`; `UNIQUE(run_id, attempt_ordinal)` + `BEGIN IMMEDIATE` (Phase 45) prevent collision; replay reads in ordinal order (research §6). |
| T-46-13 | Information disclosure/Tampering | silent candidate merging | high | mitigate | Exact structural duplicates get `duplicate` status but are retained one-row-per-attempt; diversity is recorded, never used to merge/drop (AF-REQ-19 / research Pitfall 3). |
| T-46-14 | Elevation | factory imports | high | mitigate | Static import guard + test: `alpha_factory` imports only `factor_dsl`, `factor_registry`, `run_contract` — no evaluation/provider/admission/broker (research Pitfall 6). |
</threat_model>
