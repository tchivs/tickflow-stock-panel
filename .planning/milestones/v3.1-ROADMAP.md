# Milestone v3.1: 可信工作台与运维闭环

**Status:** SHIPPED 2026-08-20
**Phases:** 51-54
**Total Requirements:** 21 (BASE-01..04, AUDIT-01..05, WORK-01..06, MON-01..06)
**Verification:** override_closeout — phases delivered directly without GSD plan/verify workflow; acceptance verified via browser walkthrough + e2e suite (101 passed / 0 failed / 4 skipped)

## Overview

v3.1 将 AthenaQuant 从量化研究平台提升为可信的投资者工作台: 每次工具调用留下脱敏审计事实, 首页一屏聚合数据质量/任务/报告/监控/待办, 报告带证据卡与冲突路径, 监控可 test-fire/预览/冷却感知。

## Phases

### Phase 51: 发布基线收口

**Goal**: 里程碑在可信基线上开工 — 规划文档与真实进度一致, 前端单测默认执行, 三项部署冒烟可运行并给出结论, v3.0 每项技债有处理或明确关闭结论。

**Depends on**: Phase 50 (v3.0, completed 2026-08-09); first v3.1 phase, no v3.1 dependency.

**Requirements**: BASE-01, BASE-02, BASE-03, BASE-04

**Success Criteria** (what must be TRUE):

1. 用户打开 STATE.md、PROJECT.md、ROADMAP.md、REQUIREMENTS.md 中任一文档, 看到的都是 v3.1 同一里程碑、同一阶段的同一状态。
2. 开发者运行一条命令即可执行 Vitest 前端单测套件并得到通过/失败汇总; vitest 成为前端依赖, 且该套件在本地/CI 检查流程中被默认纳入。
3. 开发者可在部署环境分别执行真实 LLM(两阶段分析)、Provider 降级、SSE 重连三个冒烟脚本, 每个脚本输出明确的通过/失败结论。
4. 用户可在文档中查阅 v3.0 技债清单及每项「已处理 / 明确关闭(含理由)」结论。

### Phase 52: 全局可信度与工具审计

**Goal**: Provider、AI、通知与外部工具的每次调用都留下统一、脱敏、可查询的 ToolCallEnvelope 审计事实; 统一 Provider Doctor 与数据质量 API 让降级、新鲜度与缺陷对用户可见。

**Depends on**: Phase 51

**Requirements**: AUDIT-01, AUDIT-02, AUDIT-03, AUDIT-04, AUDIT-05

**Success Criteria**:

1. Provider/AI/通知/外部工具每次调用追加一条 ToolCallEnvelope (tool/params/version/scope/response_shape/raw_hash/duration/error), 可按 principal/scope 查询; 审计只追加事实, 不改变确定性代码对生成/评估/门禁/晋级的所有权。
2. 用户在统一审计页面查看全部工具调用, 可按来源、日期、缓存、降级、schema、失败原因筛选。
3. 用户可对任一 Provider 执行 Doctor 诊断, 看到健康/降级/不可用分级结论; 诊断只读, 无自动修复。
4. 用户可通过统一数据质量 API 拉取各数据源新鲜度与缺陷摘要, 前端据此渲染质量告警。
5. 审计对外展示经过脱敏: 密钥、完整报文与个人数据不出后端, 页面/API 只能看到 raw_hash 与脱敏摘要。

### Phase 53: 今日工作台与统一待办

**Goal**: 首页成为「今天什么状态、什么信号、什么任务、什么风险、下一步点哪里」的唯一入口。

**Depends on**: Phase 52

**Requirements**: WORK-01, WORK-02, WORK-03, WORK-04, WORK-05, WORK-06

**Success Criteria**:

1. 用户在首页一屏看到数据新鲜度与 Provider 健康总览; 质量告警 Banner 与 Alpha 工作台等页面共享同一数据源。
2. 用户在首页看到运行中与失败任务及失败原因, 每项可跳转到对应运行页。
3. 用户在首页看到最近报告与研究产物入口, 每项可跳转到报告/产物详情。
4. 用户在首页看到最近监控触发记录, 可跳转到监控详情。
5. 用户在统一「待确认」收件箱看到生命周期、论点、因子晋升、纸面调仓四类待办, 每项有明确下一步入口。

### Phase 54: 监控与报告闭环

**Goal**: 监控可验证(test-fire/预算/冷却/渠道健康/digest 预览)、报告可信(质量 Banner/证据卡/引用回链/冲突与失败路径)、运行页完整(Timeline/参数/工具调用/产物/重试/SSE 恢复) — 验收主链路端到端闭合。

**Depends on**: Phase 53 and Phase 52

**Requirements**: MON-01, MON-02, MON-03, MON-04, MON-05, MON-06

**Success Criteria**:

1. 用户可对任一监控规则执行 synthetic test-fire 并看到与真实触发一致的通知预览; test-fire 不触达真实通知渠道预算以外副作用。
2. 用户可查看每个监控的预算消耗、冷却剩余时间与通知渠道健康状态; 可先预览 digest 汇总内容再启用定期投递。
3. 每份报告带数据质量 Banner、证据卡与引用回链, 读者可从任一结论跳转到原始证据(含工具调用 raw hash 与产物)。
4. 报告可展示多空冲突观点与失败路径(哪些数据/步骤不可用), 不隐藏坏消息。
5. 运行页统一展示 Timeline、参数、工具调用与产物; 失败任务可重试; SSE 断连重连后从断点恢复, 不丢失也不发明事件。

## Milestone Summary

**Key Decisions:**

- Decision: ToolCallEnvelope append-only SQLite + immutability triggers (Rationale: 审计只追加事实, 不改变业务)
- Decision: 审计脱敏白名单 + raw_hash (Rationale: 密钥/完整报文不出后端)
- Decision: 审计 seam try/finally (Rationale: 审计失败不阻塞业务)
- Decision: 工作台 API 各子项 fail-soft (Rationale: 单子项失败不阻断整体)
- Decision: 三组件共享 QK.workbench query key (Rationale: TanStack Query 自动去重)
- Decision: test-fire 不落盘/不推送 (Rationale: 保存/恢复 _last_fire 不污染冷却)
