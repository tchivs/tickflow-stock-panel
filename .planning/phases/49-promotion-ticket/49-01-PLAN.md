<open_question_resolutions>
- **R1 (expire vs conflict taxonomy) — RESOLVED, ratified here.** Hard-reject (**conflict**, `status='conflicted'`, non-recoverable, re-issue requires a new ticket) for any divergence in: candidate `canonical_expression` / `ast_signature`, `snapshot_sha256`, `manifest_sha256`, live admission policy fingerprint (`verify_admission_policy_fingerprint` mismatch), `vocabulary_fingerprint`, `grammar_fingerprint`, `membership_fingerprint`, the admission verdict (no longer `admitted` or `policy_version` changed), or the selection-OOS status. Re-issueable (**expire**, `status='expired'`) for: wall-clock `now > expires_at`, or a superseding proposal for the same candidate (a later proposal_digest supersedes the bound one). Rationale: conflict = the bound evidence is no longer the truth the reviewer approved; expire = the binding is still valid but the approval window closed. Both terminalize without producing a revision (research §2.3 R1).
- **R2 (re-verify, not re-compute) — RESOLVED, ratified here.** "Refresh" means re-reading persisted immutable facts and re-verifying them byte-for-byte. It MUST NOT call `run_admission`, re-load governed panels, re-build a `FactorSignalChain`, or re-score. The frozen snapshot has no "stale prices" (unlike PA_Agent's live RiskEngine); the verdict row is append-only and bound by `UNIQUE(revision_id, policy_version)`. The ONE thing that can drift is the live admission policy code, caught by `verify_admission_policy_fingerprint` (research §2.3). Re-running admission is an explicit anti-pattern: it would grant the promotion path computation authority over a completed run's evidence (ROADMAP non-goal, ROADMAP.md:149) and blur the no-automatic-re-scoring boundary.
- **OQ-1 (ticket table location) — RESOLVED: same SQLite DB as the run ledger.** Consume (49-02) writes the formal `FactorRevision` + catalog entry in one `BEGIN IMMEDIATE` transaction with the ticket status flip; a side DB would break that atomicity (the repository.py:2405-2444 write-fence argument, OQ-1 precedent from 48-01).
</open_question_resolutions>

## Trust Boundaries

| Boundary | Description |
|---|---|
| Frozen evidence → ticket binding | A ticket MUST bind digests/verdicts read from append-only rows, never recomputed values; a missing required fact fails closed with no ticket. |
| Issue → consume window | The binding is frozen at issue; the only value that can drift is the live admission policy code, caught by `verify_admission_policy_fingerprint`. |
| Re-verify vs re-compute | The most dangerous boundary: refresh/consume MUST NOT gain computation authority over a completed run's evidence (R2). |
