## Success-criteria evidence (AF-REQ-21 SC5, AF-REQ-26)

- **Explicit-declaration only, never an implicit fallback (R3 / D-48-04 / SC4, T-48-04a).** `is_fixture_explicitly_selected(settings)` returns `True` ONLY on an explicit, non-default selector (`fixture_mode` truthy AND `fixture_name` non-empty); it returns `False` for every missing/default/`None`/empty selector (parametrized over 8 cases). Preflight `provider_availability` (`preflight.py:251`) FAILS a production run when no real provider is configured and the fixture selector is absent; it passes only when `ai_configured(provider)` OR `is_fixture_explicitly_selected()` (D-48-04 gate). A production provider error never branches to the fixture — `test_production_provider_error_never_switches_to_fixture` runs a real-provider `Stage1Service` against a raising transport, asserts `ProviderCallError` is raised with **zero** proposal rows and **no** `offline_fixture` row synthesized.
- **Non-production label on every fixture AnalysisRecord (SC5, T-48-04b).** Every fixture-produced `research_alpha_analysis_attempts` and `research_alpha_proposals` row carries `provider='offline_fixture'` / `model='offline-fixture-v1'` (`test_stage1_proposals_labeled_offline_fixture`, `test_e2e_fixture_run_full_trace_non_production`). The fixture is a *peer* provider selectable only by explicit declaration, never a transport the production path reaches.
- **Known full deterministic trace, zero network I/O (AF-REQ-26).** `default_fixture()` returns one canned momentum Stage 1 proposal (`momentum_20d`, parses under the live DSL) + a clean advisory Stage 2 review (`disposition='retain'`, empty caveats — no referential surface), both matching the live schema versions (`STAGE_ONE_SCHEMA_VERSION`/`STAGE_TWO_SCHEMA_VERSION`). `OfflineFixtureProvider.generate_text_for(stage)` returns the canned bytes per stage and never touches the network (`test_provider_never_performs_network_io` monkeypatches `ai_provider.generate_ai_text`/`stream_ai_text` to assert).
- **Resume-from-checkpoint reuses the Phase 45 cursor (AF-REQ-21 §6.1, T-48-04c).** `resume_agent_stage()` reads `get_latest_valid_checkpoint()`'s `stage` discriminator and maps it to the next Agent stage (none/early → `stage1`; `stage2_pending` → `stage2`; `stage2` → `complete`). It validates the run is `running` and the caller holds the current attempt token. It does NOT recompute committed candidate/fold/admission/OOS evidence — those are append-only idempotent (`repository.py:2250-2358, 1078-1135`) and Stage 2 reads them. `_append_stage1_boundary()` writes the contiguous `stage1_completed` event + `stage2_pending` checkpoint in one `BEGIN IMMEDIATE` transaction (Stage1Service does not own its checkpoint). No new Agent/validation framework is introduced (ROADMAP.md:71).
- **Stale-token fence (T-48-04c).** A checkpoint written under a stale token is rejected by `append_stage_boundary`'s `expected_attempt_token_digest` fence. `recover_running_attempt()` fences the old token (issues a fresh digest); `test_stage2_boundary_with_stale_token_rejected_on_resume` recovers then asserts `resume_agent_stage` rejects the now-stale original token.
- **E2E fixture run is deterministic + resumable.** `run_fixture_mode()` orchestrates the full `preflight → stage1 → stage2 → AnalysisRecord` chain. `stop_after_stage='stage1'` exercises the resume path: a second invocation resumes from the `stage2_pending` cursor, runs ONLY Stage 2, and does NOT recompute Stage 1 proposals (`test_e2e_fixture_run_is_resumable_no_duplicate_side_effects`). Two independent runs over the same fixture produce byte-identical AnalysisRecord traces (`test_e2e_fixture_run_byte_identical_across_two_runs` asserts `response_sha256`/`request_scope_sha256`/`parsed_output_sha256` equality). A completed run is idempotent — re-running is a no-op (`test_e2e_fixture_run_idempotent_full`).
- **ExperienceLibrary seam is read-only, never a fallback (SC4, T-48-04d).** `ExperienceLibrary` is a `runtime_checkable` Protocol with a single `lookup()` that never performs a provider call (`test_empty_library_makes_no_provider_call`, `test_offline_library_makes_no_provider_call`). `EmptyExperienceLibrary` is the valid production default (yields `()`; the Agent runs without experience context). `OfflineFixtureExperienceLibrary` returns the canned entry for a matching `(factor_family, objective)` and nothing otherwise. A populated library wired as Stage 1 `experience_context` is NOT a fallback response: a provider failure still yields zero proposals (`test_populated_library_is_not_a_fallback_response`). The protocol is the only contract — a later phase adds a populated implementation without touching `agent_stage1.py`/`agent_stage2.py` (`test_protocol_contract_allows_later_implementation`).

## Deviations & decisions

1. **Plan's verification filename typo.** The plan's `<verification>` references `tests/research/test_hypotheses_workflow.py` (plural); the actual file is `tests/research/test_hypothesis_workflow.py` (singular). Ran the correct file (141 passed). `hypotheses.py` is untouched by this plan.
2. **`run_fixture_mode` takes the worker's `attempt_token` as a parameter (no internal fencing).** The orchestrator runs as the current worker; the token it presents to `resume_agent_stage` is the one issued by `start_or_resume`/`recover_running_attempt`. `append_stage_boundary` does NOT advance `transition_version` (only `last_event_seq`), so the same token + version stay valid across the stage boundaries of one attempt — internal per-stage fencing would have orphaned the original token and broken resume. Token re-fencing remains available as an explicit separate operation (`recover_running_attempt`) for the orphaned-worker case, after which the caller passes the fresh token. This matches the plan's intent: "recover fences the old token; a checkpoint written under a stale token is rejected by `expected_attempt_token_digest`".
3. **`_append_stage1_boundary` lives on `ResearchRunService`, not `Stage1Service`.** 48-04's `files_modified` excludes `agent_stage1.py`/`agent_stage2.py` (they are prior-wave artifacts). `Stage1Service.run` (48-02) does not own its own checkpoint (the 48-03 summary deviation #4 notes Stage 2 writes its own; Stage 1 was deferred to the orchestrator). The fixture orchestrator writes the contiguous `stage1_completed` + `stage2_pending` checkpoint, mirroring `Stage2Service.run`'s `append_stage_boundary` call for `stage2`. Both honor the attempt-token / version / contiguity / binding fences.
4. **Default fixture Stage 2 uses empty caveats (byte-identical, no referential surface).** An empty `caveats` array is schema-valid (`decode_stage2_payload` bounds length but does not require non-empty), and with no `evidence_refs` there is no referential-integrity surface — so the fixture trace is byte-identical across runs and cannot spuriously fail on candidate identity. The recommendation is advisory (`disposition='retain'`); `caveats` empty + `recommendation` present satisfies the closed schema. A populated Stage 2 trace citing real candidates can be supplied via a custom `FixtureTrace`.
5. **`derive_factor_family` is deterministic and declaration-order-stable.** Counts the family each permitted field belongs to (derived from `extract_features`, `factor_dsl.py:446-465`) and returns the dominant; ties resolve to `_FAMILIES` declaration order (`momentum` first), and empty/unmapped sets default to `"momentum"` (the fixture's known-good family). Identical input always yields identical output independent of iteration order.
6. **Repository region (W1 honored).** No `repository.py` changes — 48-04 reuses the 48-03 `append_stage_boundary` / `next_checkpoint_version` / `get_latest_valid_checkpoint` and the 48-01 analysis-attempt ledger verbatim. All 48-04 additions land in new modules (`agent_fixture.py`, `agent_experience.py`) and in the `run_service.py` Phase 48-04 region.
