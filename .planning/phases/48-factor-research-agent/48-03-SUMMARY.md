## Success-criteria evidence (AF-REQ-13 SC3, AF-REQ-21)

- **Frozen inputs + server evidence only (read-only).** `StageTwoRequest` carries a frozen `snapshot_ref` (bounded-JSON-validated provenance digests) and a `ServerEvidence` projection assembled **read-only** by `assemble_server_evidence` from `list_candidates` + `list_alpha_fold_evidence` + `list_admission_verdicts_for_run` (Phase 47 ledger). The model authors nothing it consumes; a clean Stage 2 run performs no candidate/OOS/promotion write (`test_stage2_service_read_only_no_candidate_write`).
- **No mutable field (schema-level SC3, T-48-03a).** `decode_stage2_payload` is pure (no provider call, no input mutation) and enforces `extra='forbid'` at **every** nesting level (top, caveat, evidence_ref, recommendation) with field-specific `ValueError`s. A second-layer `MUTABLE_FIELD_NAMES` scan (symmetric to `assert_admission_no_edit`, alpha_scoring.py:479-505) rejects any key carrying `expression`/`metric`/`threshold`/`oos`/`admission`/`score`/`override` — including aliased substring forms (`expression_override`, `oos_flag`, …) — at top level, inside a caveat, or inside the recommendation (parametrized over all 7 tokens × 3 locations). `disposition` is the only action and it is advisory; `follow_up_run_dims` may only accompany `disposition='propose_new_run'`.
- **Referential integrity (OQ-2, T-48-03b).** Every cited `evidence_refs[].id` resolves within `run_id`: `candidate` → `candidate_exists_in_run`, `evaluation` → `fold_evidence_exists_in_run`, `gate` → `admission_verdict_exists_in_run` (the verdict **ROW** bound to a candidate in the run via `candidate_trail.provenance.run_id`; a bare non-verdict gate id resolves to nothing), `artifact` → `artifact_exists_in_run`. Same-run citations across all four kinds resolve; a fabricated or cross-run reference is a permanent `ReferentialIntegrityError` with a bounded machine-readable `{kind, id, run_id}` detail — no fallback review. The check performs only bounded `SELECT` reads.
- **Stage-boundary checkpoint (AF-REQ-21 §6.2, T-48-03d).** `append_stage_boundary` writes the terminal stage event AND its checkpoint in ONE `BEGIN IMMEDIATE` transaction, reusing the attempt-token/version fence, snapshot/manifest binding, server-allocated event seq, event-contiguity guard, and referenced-candidate/artifact resolution. Stage 1 boundary → `stage2_pending`; Stage 2 boundary → `stage2` (terminal for the Agent). A non-contiguous `committed_event_seq` or stale token is rejected with **zero** partial commit (`test_boundary_non_contiguous_committed_event_seq_rejected`, `test_boundary_stale_attempt_token_rejected`).
- **No fallback (SC4) + advisory recommendation (T-48-03c).** A provider/decode/referential failure produces **zero** validated rows and a failed `research_alpha_analysis_attempts` row, raises `ProviderCallError`, and writes no checkpoint. `disposition='propose_new_run'` is recorded as advisory inline-summary data only — the runs-table count is unchanged (`test_stage2_service_propose_new_run_does_not_spawn_run`).

## Deviations & decisions

1. **AgentProviderSeam transport outcome is now always `proposed`.** The seam (48-01) recorded `outcome="proposed" if stage=="stage1" else "validated"`, so a Stage 2 transport row was prematurely `validated` before decode/referential checks — which would leave a `validated` row on a decode/referential failure, violating the 48-03-03 acceptance ("ZERO validated rows"). Refined to `outcome="proposed"` for **all** stages: transport success means "a response was proposed"; each Stage service records the terminal outcome after its own server-side checks (Stage 2 records `validated` only after decode + referential integrity pass). Safe: every 48-01 seam test uses `stage="stage1"` and asserts `proposed` (unchanged); no test asserted a stage2 transport `validated` row. This is a one-line refinement to 48-01 code in service of 48-03-03's no-fallback invariant.
2. **`gate` ref binds via `candidate_trail.provenance.run_id`.** The admission verdict table (`factor_admission_verdicts`) is revision-scoped (no `run_id` column), shared platform-wide. OQ-2 resolved: a Stage 2 caveat cites the verdict **row** id (not individual gate ids — the row already lists every gate's value/threshold/reason, alpha_scoring.py:287-418). `admission_verdict_exists_in_run(run_id, verdict_id)` reads the verdict row and confirms `candidate_trail.provenance.run_id == run_id` — the binding the verdict row itself carries (mintered by `record_candidate_admission`). A bare non-verdict id resolves to nothing and is rejected (`test_gate_non_verdict_id_resolves_to_nothing`).
3. **`append_stage_boundary` is layered service + repository.** The plan signature lives on `ResearchRunService` (validates stage→checkpoint mapping, recomputes `checkpoint_version` + `state_checksum` and asserts the caller-supplied checksum matches, generates `checkpoint_id`). The atomic event+checkpoint transaction is `ResearchRepository.append_stage_boundary` (owns the single `BEGIN IMMEDIATE` connection — the service cannot span two repo calls in one transaction). Both honor the plan: the service method takes `after_stage`/`checkpoint_stage`/`state_checksum` (no `checkpoint_version`/`checkpoint_id` — those are internally derived) and `entity_kind`/`entity_id` are pinned to `run`/`run_id` for stage events. `checkpoint_version` is internally `MAX(checkpoint_version)+1` via `next_checkpoint_version`, so successive boundaries never collide on the cursor-identity checksum.
4. **Stage 2 does not transition the run to `completed`.** The 48-03-03 acceptance requires a `validated` attempt + `stage2_completed` event + contiguous checkpoint; it does not require the run→`completed` lifecycle transition (that is the orchestrator's / 48-04's job, and Phase 49 catalog promotion is downstream). `Stage2Service.run` writes the `stage2` checkpoint and leaves the run `running` under its live attempt token so resume (48-04) reads the contiguous cursor.
5. **`research_alpha_analysis_attempts` `failure_class` for referential integrity = `schema_violation`.** The 48-01 taxonomy has no dedicated referential class; a Stage 2 referential-integrity failure is a permanent server-side validation failure of the model's output, recorded as `failure_class='schema_violation'` with a `referential_integrity` validation-error code (mirroring how Stage 1 records decode failures as `schema_violation`/`malformed_json`). Decode failures keep `malformed_json`/`schema_violation` exactly as Stage 1 does.
6. **Repository region (W1 honored).** All 48-03 `repository.py` additions (`candidate_exists_in_run`, `fold_evidence_exists_in_run`, `admission_verdict_exists_in_run`, `artifact_exists_in_run`, `list_admission_verdicts_for_run`, `next_checkpoint_version`, `append_stage_boundary`) land in the evidence-read + checkpoint region (after the AnalysisRecord/Stage-1-proposal block, around `append_checkpoint`) — distinct from 48-02's proposal store. They are additive bounded reads/one atomic writer; `alpha_scoring.py` is not modified.
