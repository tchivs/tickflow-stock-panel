# 36-02 PLAN — Full-Universe Run Execution + Monitoring + Verification (FA-04/FA-05)

**Phase**: 36 全量竞价回填 — wave 2 (runs in parallel with 36-03, after 36-01 lands)
**Requirements**: FA-04 (execution support), FA-05 (documentation stance).
**Depends on**: 36-01 (CLI + `only_missing` + timeout exemption landed and batch-green), RESEARCH.md measured anchors (5537 universe / 248 days / 3.5-5.5h / 13MB / BJ 333 empty).
**Guards**: zero new deps · read-only verification only (no backfill forgery) · coverage ≤94.0% never claimed 100% · no frontend.

## Goal

Make the sandbox full-universe run **executable, observable, recoverable, and provable**: the detached launch runbook (with EOD-window discipline), the progress-monitoring procedure (log polling, `/tmp` log, tail), the `--only-missing` top-up procedure, a repeatable acceptance-verification checklist (partition count 248, rows ≈1.29M, no `.tmp`, virtual_price==open cross-check, BJ ledger), and the FA-05 honest-coverage stance document (BJ gap, 5 tested code formats, ≤94.0% framing).

This wave produces **procedure + evidence tooling**, not the run itself — the orchestrator launches per 36-01 T7; this plan defines how it is monitored, topped up, and verified, and how the honest BJ ceiling is documented.

## Tasks

### T1. FA-04 — Detached launch runbook (executed by orchestrator)

**Files**: this plan (runbook lives here; no code). Sequence:

1. **Preflight** (36-01 landed, batch green):
   ```
   cd backend && .venv/bin/python -m pytest tests/test_auction_backfill_full_universe.py -k "timeout or reap or only_missing or cli" -q
   cd backend && .venv/bin/python scripts/auction_backfill.py --help          # exit 0, six flags listed
   ```
   Lake sanity: `data/kline_auction` has 248 partitions, 2 symbols, 496 rows (32-02 anchor) — the run will grow it to ~5204 symbols.
2. **Launch** (first run, **no** `--only-missing`, so acceptance numbers are exact — the 2 pilot symbols re-fetch idempotently):
   ```
   # primary (this harness) — detached:true survives broker/omp exits; cwd=backend
   hub op=start name=auction-backfill application=.venv/bin/python \
     args=["scripts/auction_backfill.py","--all","--rpm","30","--out","/tmp/auction-backfill-<TS>.json"] \
     cwd=backend detached=true ready={"log":"\\[progress\\]"}

   # bare-metal nohup equivalent:
   cd backend && nohup .venv/bin/python scripts/auction_backfill.py --all --rpm 30 \
     --out /tmp/auction-backfill-$(date +%Y%m%d-%H%M%S).json \
     > /tmp/auction-backfill-$(date +%Y%m%d-%H%M%S).log 2>&1 &
   ```
   Replace `<TS>` with the launch timestamp; record PID (nohup `$!` / `hub ps`).
3. **EOD-window discipline** (FA-06): launch **outside** the EOD `run_all` window. The CLI is a separate process from the API server — the `kline_auction` write seam has **no cross-process lock** (read-modify-write + atomic rename, last-rename-wins); the in-process run slot serializes only within one process. A nightly/off-hours start is the mitigation. Do **not** trigger EOD `run_all` (or manual `/api/pipeline/run`) while the backfill is running.
4. **Runtime expectation**: rpm 30 pacing 2.0s/slot × 5537 ≈ 3.1h minimum; workload ~1.9s/request+write → measured total 3.5-5.5h (RESEARCH §3.4). BJ 333 symbols consume ~3-6 min of requests and produce 333 expected `empty_response` ledger entries — not an anomaly.

**Acceptance**: process is detached and alive (`hub ps` / `ps -p <pid>`); `/tmp/auction-backfill-*.log` exists and shows `[progress]` lines advancing; the run is outside the EOD window.

### T2. FA-04 — Progress monitoring procedure

**Procedure** (operator, during the 3.5-5.5h run):
- **Primary**: `hub logs auction-backfill --follow` (or `tail -f /tmp/auction-backfill-*.log`).
- **Progress signal**: `[progress] 覆盖扫描: 跳过 N 已全覆盖, 待回填 M` at start (M=5537 on the first run), then `[progress] i/5537 (成功 X, 失败 Y)` per symbol — a full line every ~2.2-2.5s.
- **Expected noise**: `[progress]` lines are the only traffic; `429/限速` retry warnings are expected and self-heal via the 2s→4s backoff (`auction_backfill.py:102-121`); the upstream probe is called once at the gate, not per symbol.
- **Stall detection**: log tail unchanged for >10 min → verify the process is alive (`hub ps` / `ps -p <pid>` / `/proc/<pid>/status`); a dead process is recoverable — rerun with `--all --only-missing` (T3) instead of restarting from zero. **Never** SIGKILL a healthy run to "restart faster" — the whole point of FA-02 is that an interrupted run resumes by skip, not by waste.
- **Do not read the ledger JSON mid-run** (`--out` file is written only at completion — a missing file is not a failure signal).
- **Completion signal**: process exits; `hub wait name=auction-backfill for=exit` returns; log tail shows the human summary; ledger JSON exists.

**Acceptance**: at any point mid-run the operator can state: process alive, current `i/5537`, success/failure counts, expected ETA; a stall is detected within ~10 min.

### T3. FA-04 — Top-up procedure (`--only-missing` until stable)

**Procedure** (after the initial run completes):
1. **Top-up run**: `hub op=start name=auction-backfill-topup ... args=["scripts/auction_backfill.py","--all","--only-missing","--rpm","60","--out","/tmp/auction-backfill-topup-<TS>.json"]` (or nohup equivalent). Expect: `覆盖扫描: 跳过 5537 已全覆盖, 待回填 0` → terminal dict `requested=0`, exit 0.
2. **Run twice consecutively**; both must report `requested == 0 / backfilled_symbols == 0` → **top-up stable** (FA-04 acceptance). If the first top-up reports nonzero `backfilled_symbols` (e.g. interrupted residue from a mid-run crash, or upstream newly added BJ/SZ codes), rerun until two consecutive zero-runs.
3. **Idempotency proof**: each top-up's terminal dict is the ledger evidence; `test_full_backfill_only_missing_skips_fully_covered` locks the skip semantics at unit level.

**Acceptance**: two consecutive `--only-missing` runs report 0 new rows; ledger JSONs saved as evidence.

### T4. FA-04 — Read-only verification tool `backend/scripts/verify_auction_backfill.py`

**Files**: new `backend/scripts/verify_auction_backfill.py` (read-only; zero new deps; uses the same DuckDB views the repo builds — `kline_auction` repository.py:169-171, `kline_daily` :162-164; no writes, no network).

**Outputs** (printed checklist, all derived from the lake, not from the ledger claim):
1. Universe: distinct symbols in `kline_daily` → 5537; split SZ/SH/BJ (2894/2310/333); kline_daily total rows (1,326,996 anchor).
2. Lake state: `kline_auction` partition count (date=* dirs → **248**), total rows (**≈1,290,592**), distinct symbols (**≈5204**).
3. BJ ledger re-derivation: symbols in `kline_daily` with suffix `.BJ` (920xxx) **missing** from `kline_auction` → count (**333**) and the full list sampled — the honest `empty_response` set, independently of the run's ledger.
4. Cross-check: for ≥3 dates × all symbols, `auction_virtual_price == kline_daily.open` on the same (symbol, date) — report mismatch count (must be 0). Query shape:
   ```sql
   SELECT COUNT(*) FROM kline_auction a
   JOIN kline_daily d ON a.symbol = d.symbol AND CAST(a.datetime AS DATE) = d.date
   WHERE d.date IN (?, ?, ?) AND a.auction_virtual_price IS NOT NULL
     AND abs(a.auction_virtual_price - d.open) > 1e-6
   ```
5. `.tmp` residue scan: `kline_auction` tree contains no `*.tmp` files.
6. Coverage framing: `auction_symbol_count / 5537` printed as e.g. `0.940` — **never** rendered as 100%.

**Acceptance**: `cd backend && .venv/bin/python scripts/verify_auction_backfill.py` exits 0 and prints all six facts; on the pre-run lake it reports 2 symbols/248 partitions/496 rows (honest baseline); post-run it reports the FA-04 numbers.
