## 1. System Classification

**System Type:** Hybrid — a bounded, stateful research workflow combining governed evidence retrieval, structured investment-analysis generation, and lifecycle tracking; it is not an autonomous agent.

**Description:**
Phase 3 turns governed market, portfolio, and research evidence into an investor-inspectable analysis. Every material claim retains A/B/C source-quality context, a cross-check result or explicit unresolved state, and a structured rationale. The workflow produces a multi-perspective report, valuation only when the supplied evidence makes it applicable, an IC memo, and an immutable history of signal lifecycle transitions. Good output is evidence-grounded, schema-valid, reproducible from recorded inputs, and clearly distinguishes observations from analytical judgment; it never places orders, executes tools beyond approved data reads, or autonomously advances a research decision.

**Critical Failure Modes:**
1. A material number is stated without source provenance, source-quality grade, or a cross-check/unresolved disclosure (ANLY-01).
2. The report invents or obscures a valuation conclusion, scoring rationale, perspective disagreement, or IC recommendation (ANLY-02).
3. A lifecycle status changes without an attributable evidence event, timestamp, prior status, or reviewable outcome history (ANLY-03).
4. Untrusted retrieved text overrides workflow instructions, is treated as a source of authority, or contaminates a structured output.
5. Model output performs or recommends live trade execution instead of bounded research analysis.

## 1b. Domain Context

**Industry Vertical:** 面向个人 A 股投资者的自托管量化投研与投资决策支持。  
**User Population:** 需要核验市场、财务、持仓与研究证据，并自行作出投资决定的个人投资者／研究者。  
**Stakes Level:** High——错误的研究结论可能造成真实资金损失、错误风险暴露和对数据可信度的误判；本阶段不下单、不代客操作。  
**Output Consequence:** 用户会据此审阅市场或组合判断、多视角报告、估值（仅适用时）和 IC 备忘录，并持续检验研究信号。输出必须让用户能追溯证据、看见未解决分歧与假设后自行决定，不能把分析伪装成确定收益、个性化投资建议或执行指令。

### What Domain Experts Evaluate Against

**Dimension: 证据出处与独立交叉核验**  
**Good (domain expert would accept):** 每个会改变结论的事实或数字（如价格、净利润、EPS、估值倍数、股本、公告日期）都能定位到来源标识、发布主体、发布日期/截至时点、报告期与 A/B/C 质量级别；交叉核验明确列出第二来源、是否独立、结果（相符/差异/无法核验）及差异原因。将同一供应商转载、同一公告镜像或同一底层数据的两个页面标为“独立来源”是不允许的。  
**Bad (domain expert would flag):** 只给链接或笼统“据公开资料”，省略时点和质量级别；把相互复制的资讯当双重确认；遇到冲突时静默选择更支持结论的数字。  
**Stakes:** Critical  
**Source:** Phase 3 ANLY-01 的 A/B/C 与跨源核验合同；[FinanceBench](https://arxiv.org/abs/2311.11944) 以答案和证据片段共同评测金融问答；《[证券、期货投资咨询管理暂行办法](https://xzfg.moj.gov.cn/law/download?LawID=500&type=pdf)》第二十条要求完整、客观、准确使用资料并注明出处。

**Dimension: 重大数字的口径、期间与计算可复算性**  
**Good (domain expert would accept):** 对每个核心数字和派生比率同时呈现币种、单位、合并/母公司口径、报告期或 TTM/FY、复权/未复权定义、原始值与公式；跨源数值先按相同口径比较，公告更正、单位差异或截至时点不一致须显式说明，而非直接合并为一个“事实”。  
**Bad (domain expert would flag):** 混用元/万元/百万元、季度/年度/TTM、复权/未复权价格或更正前后财报；把模型自行计算的数写成来源原文，或在无法对齐时给出精确比率。  
**Stakes:** Critical  
**Source:** 金融研究中的可审计计算惯例；[FinBen](https://arxiv.org/abs/2402.12659) 覆盖信息抽取、问答、风险、预测与决策等金融任务，并报告模型在复杂任务上存在困难。

**Dimension: 投资论证、分歧与估值适用性**  
**Good (domain expert would accept):** 报告把已证实事实、分析假设和推断结论分层；多视角分别给出支持/反对证据、评分理由及未解分歧。估值仅在业务与输入证据足以支撑相应方法时提供，列出关键驱动、情景、限制和计算链；不适用时明确标为“不适用”及原因。IC 备忘录应表达可证伪的判断和待验证条件，而非替用户作出交易决定。  
**Bad (domain expert would flag):** 用漂亮叙事掩盖单边证据；评分无规则、无权重或无证据；对亏损、口径不足或关键输入冲突的标的仍输出确定目标价/单点内在价值，或把概率性观点写成事实。  
**Stakes:** High  
**Source:** Phase 3 ANLY-02 合同；[FinBen](https://arxiv.org/abs/2402.12659) 对广泛金融任务的结果表明，通用模型在复杂推理、文本生成与预测上不应被视为可直接替代专业判断。

**Dimension: 信号生命周期与结果完整性**  
**Good (domain expert would accept):** 每次“增强、减弱、证伪、已计价”状态转换均保留前状态、时间戳、触发证据、操作者/系统归因、证据当时可得性和理由；结果复盘固定观察窗口、基准与指标定义，保留正反例及未结论信号，允许追溯而不改写历史。  
**Bad (domain expert would flag):** 没有新证据便翻转状态；事后以已知价格或后来披露的信息补写当时理由；只保留成功信号、变更历史被覆盖，或将“已计价”误写成“判断正确”。  
**Stakes:** High  
**Source:** Phase 3 ANLY-03 的可审阅结果历史合同；金融投研的事后偏差与幸存者偏差控制实践。

**Dimension: 研究工具边界与风险表述**  
**Good (domain expert would accept):** 输出明确为研究与决策支持，风险、数据局限、不确定性与利益冲突/缺失信息可见；拒绝保证收益、以传言或疑似内幕信息补足证据、代客交易或调用交易执行。用户始终保有独立决定权。  
**Bad (domain expert would flag):** 将模型结论表述为“必涨”“保证收益”或可直接执行的个性化买卖指令；把市场传言、未核实社媒内容或内幕信息当作有效证据；把研究工作流扩展为自动交易。  
**Stakes:** Critical  
**Source:** 《[证券、期货投资咨询管理暂行办法](https://xzfg.moj.gov.cn/law/download?LawID=500&type=pdf)》第二十一、二十二、二十四条对虚假/传言/内幕信息、风险说明、收益承诺和代理买卖的限制；项目“自动实盘经纪订单执行”明确为范围外。

### Known Failure Modes in This Domain

1. **伪交叉核验与时间错配：**两个页面实为同一底层数据或转载，却被标为独立确认；或将财报更正前后、公告日与报告期、盘中与收盘时点混合，使看似“已核验”的结论不可复现。
2. **数字口径漂移：**单位、币种、合并范围、复权方式、季度/FY/TTM 或分母定义被悄然替换，导致 EPS、PE、增长率和仓位相关结论在算术正确但经济含义错误的情况下输出。
3. **叙事替代论证：**模型把弱证据串成单边投资故事，虚构评分依据、估值输入或反方观点；在估值不适用、关键数据冲突或预测高度不确定时仍给出精确目标价和确定性结论。
4. **生命周期事后改写：**信号状态没有可归因的证据事件，或复盘使用当时不可得信息、仅展示成功案例，导致“强化/证伪/已计价”和表现归因无法审计。

### Regulatory / Compliance Context

本阶段定位为自托管的研究与决策支持，且不含自动下单、代客交易或收益承诺；这一定位**不等同于法律结论或豁免**。中国《[证券、期货投资咨询管理暂行办法](https://xzfg.moj.gov.cn/law/download?LawID=500&type=pdf)》第二、三条将通过电脑网络等形式直接或间接有偿提供证券、期货投资分析、预测或建议纳入证券、期货投资咨询并要求业务许可。因此，若未来将功能对外提供为有偿、面向客户的具体证券分析/预测/建议服务，应在上线前由具备资质的中国证券合规/法律专业人士审查服务模式、牌照、人员资格、营销与留痕义务；本规范不据此断言当前内部工具必然受该许可制度约束。

无论部署边界如何，产品设计应以该办法第二十至二十四条体现的审慎原则作为最低研究质量约束：资料完整、客观、准确且可注明出处；不得以虚假信息、市场传言或内幕信息为依据；不得保证收益、与用户分成/共担损失或代为买卖。对 Phase 3，这落实为来源披露、风险与局限提示、不可覆盖的审计历史，以及阻止研究输出转化为执行指令；不扩大为自动化交易或持牌投资顾问服务。

## 2. Framework Decision

**Selected Framework:** LangGraph

**Version:** 1.x (pin the exact compatible release in the Phase 3 implementation lockfile)

**Rationale:**
LangGraph fits a bounded, explicitly modeled research workflow rather than an autonomous agent: named nodes and typed state make source grades, cross-check outcomes, report rationale, valuation applicability, IC memo, and lifecycle transitions inspectable and replayable. Checkpointed state supports ANLY-03 history while deterministic conditional transitions prevent the Phase 3 system from choosing or executing actions. Its Python support aligns with the existing FastAPI/Pydantic backend, and model adapters can remain behind the current OpenAI-compatible boundary.

**Alternatives Considered:**

| Framework | Ruled Out Because |
|-----------|------------------|
| Haystack 2.x (Python) | A strong alternative for a strictly linear, explicit pipeline, but it has less natural support for checkpointed, branching lifecycle workflow state and replay across ANLY-01/02/03. |
| LlamaIndex | Retrieval quality is important, but the primary need is auditable state transitions and structured analysis orchestration rather than an ingestion-first RAG framework. |

**Vendor Lock-In Accepted:** Partial — LangGraph is model-agnostic, but its graph/checkpoint API is adopted; model calls remain provider-configurable behind the existing compatible adapter.

## 3. Framework Quick Reference

### 安装与版本闸门

LangGraph Python 使用 **1.x**；实施时必须将实际解析的 `langgraph`、Pydantic 和可选 `langchain-openai` 版本精确写入锁文件。`durability="sync"`、持久化 saver 与流式事件格式必须针对该锁定版本进行集成烟测；`astream(..., version="v2")` 需 LangGraph ≥1.1，低版本不得依赖它。

```bash
pip install "langgraph==1.0.8" "pydantic>=2.7,<3"
# 仅当现有 OpenAI-compatible 边界已通过兼容性测试时使用：
pip install "langchain-openai"
```

`langgraph` 不要求 LangChain 或单一模型供应商；模型调用仍在现有 OpenAI-compatible SDK/适配器边界之后。

### 核心导入与固定入口图

```python
from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph


class AnalysisState(TypedDict):
    research_id: str
    source_records: list[dict[str, object]]
    signal_lifecycle: dict[str, object]
    report: dict[str, object] | None


async def validate_inputs(state: AnalysisState) -> dict[str, object]:
    # 实现中以 Pydantic 验证，不原地修改 state。
    return {"source_records": state["source_records"]}


async def generate_report(state: AnalysisState) -> dict[str, object]:
    return {"report": {"research_id": state["research_id"]}}


builder = StateGraph(AnalysisState)
builder.add_node("validate_inputs", validate_inputs)
builder.add_node("generate_report", generate_report)
builder.add_edge(START, "validate_inputs")
builder.add_edge("validate_inputs", "generate_report")
builder.add_edge("generate_report", END)
graph = builder.compile(checkpointer=InMemorySaver())
```

这是固定的两节点 DAG，而非 agent loop：没有 `ToolNode`、`create_agent`、模型决定的边、重试循环边或下单工具。批准的数据只读获取在图外完成；图只验证冻结证据并产生可审阅研究报告。

### 关键抽象

| LangGraph 抽象 | 本阶段用法 | 不可越过的边界 |
|---|---|---|
| `StateGraph(AnalysisState)` | 描述一次运行的证据、生命周期快照和最终报告 | 不保存 SDK client、密钥或可执行工具。 |
| 节点 | `validate_inputs` 验证确定性输入；`generate_report` 调用注入的结构化模型 | 节点返回局部 state update，不原地 mutation。 |
| 固定边 | `START → validate_inputs → generate_report → END` | 生命周期变更仅由专用领域服务/人工请求创建，不是模型边。 |
| checkpointer / `thread_id` | 每个服务端生成 `research_id` 对应稳定、长度受限的运行线程 | checkpoint 不是真相库，不能替代 append-only 生命周期事件表。 |
| Pydantic 输出 | 模型只生成报告主体 | 服务端注入来源和生命周期；模型不能分级、伪造 cross-check 或推进状态。 |

### 常见陷阱

1. 启用 checkpointer 后遗漏 `{"configurable": {"thread_id": ...}}`，使运行无法可靠保存/恢复；`research_id` 必须服务端生成。
2. 将 `InMemorySaver` 用于生产：进程重启即丢状态。生产需按锁定版本选用持久化 saver，并设置保留期、访问控制、备份与迁移。
3. 将 checkpoint 误作不可变信号历史：回放可能重跑 checkpoint 后节点（含模型调用）。ANLY-03 必须以 `prior_state`、`next_state`、`occurred_at`、`evidence_id` 追加保存。
4. 让网页/公告原文控制图：外部文本是不可信数据；服务端固定 system prompt，模型无写权限、无工具、无执行权限。
5. 将所有“OpenAI-compatible”端点视为官方 OpenAI：若不通过结构化输出能力测试，适配器必须以 `Pydantic.model_validate_json()` 验证，不可静默降级为自由文本。

## 4. Implementation Guidance

### 固定执行模式

1. **图外、只读证据准备：**批准的数据服务完成 A/B/C 分级和物料数字跨源核验，冻结为 `SourceRecord`。未解决冲突保持 `unresolved`/`conflicting`，不可由 LLM 消除。
2. **图内校验与写作：**Pydantic 先验证输入；结构化模型生成多视角、估值和 IC memo；服务端二次验证并注入权威来源与生命周期快照。
3. **图外持久化：**服务层保存最终 `AnalysisReport`、prompt/model/schema 版本、证据 fingerprint、token 用量和 checkpoint 引用。生命周期只能由带证据事件的 append-only 服务变更。
4. **禁止范围：**无实时交易、下单、资产转移、网页浏览、任意工具调用、自动提升研究结论或自动推进信号状态。

### 模型适配器与配置

仅对通过兼容性测试的 OpenAI-compatible 端点使用 LangChain 适配器；`settings` 来自既有 Pydantic settings/secret store，而非请求体。`with_structured_output()` 是模型层 API，不是 LangGraph API，因此应同 LangGraph 精确锁版并在启动烟测验证。

```python
from langchain_openai import ChatOpenAI

from app.analysis.schemas import GeneratedAnalysis
from app.config import settings

chat_model = ChatOpenAI(
    model=settings.ai_model,
    base_url=settings.ai_base_url,
    api_key=settings.ai_api_key,
    temperature=0,
    max_tokens=2_000,
    timeout=30,
    max_retries=2,  # 仅传输/临时供应商失败
)
structured_report_model = chat_model.with_structured_output(GeneratedAnalysis)
```

锁版时确认提供商的 `max_tokens`/`max_completion_tokens` 参数语义。若直接使用既有 SDK，适配器仍必须提供 `ainvoke(messages) -> GeneratedAnalysis` 并执行 `GeneratedAnalysis.model_validate_json(raw_json)`；这是模型无关的验证路径，而不是自由文本退路。

### 审计与状态规则

- 模型只可生成 `GeneratedAnalysis`；`SourceRecord` 和 `SignalLifecycleState` 由确定性服务加载、验证并注入 `AnalysisReport`。
- 报告仅在二次校验成功后持久化。校验失败以明确错误结束，保留失败原因供人工重试，不返回“差不多正确”的散文。
- FastAPI 请求处理器使用 `await graph.ainvoke(...)`；不得在 ASGI event loop 调用 `asyncio.run()` 或在 async 节点调用阻塞 SDK。
- 原始长文本保存受控引用与 fingerprint，不在每个 checkpoint 中复制；模型配置、prompt、schema 和证据 fingerprint 随报告保存以支持重现。

## 4b. AI Systems Best Practices

### 4b.1 Structured Outputs with Pydantic

`GeneratedAnalysis` 是模型可生成的最小主体；`AnalysisReport` 才是 API/持久化契约。来源记录和生命周期由服务端注入，阻止模型伪造 provenance 或改变 ANLY-03 状态。

```python
from datetime import datetime
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator


class SourceRecord(BaseModel):
    model_config = ConfigDict(extra="forbid")
    source_id: str
    title: str
    url: str
    retrieved_at: datetime
    source_grade: Literal["A", "B", "C"]
    cross_check_state: Literal["confirmed", "conflicting", "unresolved", "not_required"]
    cross_check_source_ids: list[str] = Field(default_factory=list)
    material_number_ids: list[str] = Field(default_factory=list)

    @model_validator(mode="after")
    def confirmed_needs_peer(self) -> "SourceRecord":
        if self.cross_check_state == "confirmed" and not self.cross_check_source_ids:
            raise ValueError("confirmed cross-check requires peer source ids")
        return self


class Perspective(BaseModel):
    name: Literal["fundamental", "technical", "risk", "market"]
    stance: Literal["supports", "opposes", "neutral"]
    score: int = Field(ge=0, le=100)
    rationale: str = Field(min_length=1)
    evidence_ids: list[str] = Field(min_length=1)


class ValuationAssessment(BaseModel):
    applicable: bool
    method: Literal["dcf", "ddm", "relative", "asset_based", "not_applicable"]
    conclusion: str
    evidence_ids: list[str] = Field(default_factory=list)

    @model_validator(mode="after")
    def method_matches_applicability(self) -> "ValuationAssessment":
        if self.applicable == (self.method == "not_applicable"):
            raise ValueError("valuation applicability and method disagree")
        return self


class ICMemo(BaseModel):
    recommendation: Literal["research_only_watch", "watch", "reject", "escalate_human_review"]
    thesis: str
    risks: list[str] = Field(min_length=1)
    invalidation_conditions: list[str] = Field(min_length=1)
    evidence_ids: list[str] = Field(min_length=1)


class SignalLifecycleState(BaseModel):
    signal_id: str
    current_state: Literal["active", "strengthened", "weakened", "falsified", "priced_in", "closed"]
    history: list[dict[str, object]]


class GeneratedAnalysis(BaseModel):
    model_config = ConfigDict(extra="forbid")
    perspectives: list[Perspective] = Field(min_length=2)
    valuation: ValuationAssessment
    ic_memo: ICMemo


class AnalysisReport(GeneratedAnalysis):
    source_records: list[SourceRecord] = Field(min_length=1)
    signal_lifecycle: SignalLifecycleState

    @model_validator(mode="after")
    def cites_only_supplied_sources(self) -> "AnalysisReport":
        allowed = {source.source_id for source in self.source_records}
        cited = set(self.valuation.evidence_ids) | set(self.ic_memo.evidence_ids)
        for perspective in self.perspectives:
            cited.update(perspective.evidence_ids)
        if unknown := cited - allowed:
            raise ValueError(f"unknown evidence ids: {sorted(unknown)}")
        return self
```

对通过测试的端点使用 `.with_structured_output(GeneratedAnalysis)`；否则适配器请求 JSON 后调用 `GeneratedAnalysis.model_validate_json(raw)`。每次研究最多 **1 次初始生成 + 2 次仅针对 schema/引用校验错误的修复尝试**；记录 `research_id`、attempt、模型/适配器/schema 版本、错误字段、耗时和 token，但不在普通日志写入密钥或完整不可信原文。三次失败返回可审计 `validation_failed`/人工复核状态，不产生部分报告。

### 4b.2 Async-first 与流式边界

- FastAPI 路径和节点使用 `async def` 与 `await graph.ainvoke(...)`；不要在运行中的 ASGI event loop 使用 `asyncio.run()`。
- 最终报告必须 schema 校验，完成路径使用 `ainvoke`，且仅在二次验证 `AnalysisReport` 后成功返回。
- UI 只可通过既有 SSE 展示“证据已校验／生成中／校验完成”等受控进度；不能将未验证 token 作为投研结论展示或持久化。
- 若锁定 LangGraph ≥1.1 后确需事件流，可用 `astream(..., stream_mode="updates", version="v2")`；低版本不复制该调用，且不流出未验证证据回显。

### 4b.3 Prompt Engineering Discipline

- 服务端固定 system prompt：只可引用 supplied `source_id`、不得修改 grade/cross-check/lifecycle、禁止工具和交易、仅返回 schema；不拼入未经处理的原文。
- user message 仅携带 Pydantic 验证的来源、允许 ID、核验状态、研究范围与生命周期快照；外部文本一律是不可信数据，不能改变指令优先级。
- 少样本示例固定在版本化模板；动态上下文仅能来自冻结且可追溯的 `SourceRecord`。显式设定 `max_tokens`、timeout，并保存 prompt/schema/model/证据 fingerprint。

### 4b.4 Context Window Management

先确定性筛选相关来源片段、物料数字、A/B/C 与 cross-check；按来源等级、相关性、时效和物料数字排序。截断/摘要须保留 `source_id`、位置、原因和 hash。无法容纳时减少低优先级材料，或返回 `context_insufficient`/`unresolved` 交人工补充；摘要作为派生来源留存输入 fingerprint。只将当前状态及相关少量事件提供给模型，完整生命周期由 API 按需读。

### 4b.5 Cost、延迟与缓存预算

单次成本按调用时供应商价表计算：$C_{run}=\frac{T_{in}}{10^6}P_{in}+\frac{T_{out}}{10^6}P_{out}$。最多三次 schema 生成，另计受限 transport retry；服务配置每次/每日 token 与成本上限。缓存键必须包含证据、cross-check、生命周期、prompt、schema、模型及参数 fingerprint，任一来源或状态改变即失效。数值比对、来源分级、引用白名单与生命周期校验均为确定性服务，不调用 LLM；记录节点排队/模型/校验耗时、tokens、重试与缓存命中，超预算则进入人工复核而不降低 provenance 或校验。
