## Policy-transition ownership and rule

- **Schema ownership:** Reuse the existing immutable `advanced_jobs → advanced_authorizations → advanced_policy_revisions` foreign-key lineage as the creation-charge provenance. Do not add a mutable policy field, reset a window, merge revisions, migrate consumption, or introduce another datastore.
- **Query ownership:** Add one narrow `AdvancedRepository` query that resolves a queued job's authorization-backed creation policy revision. It returns no value for a missing or inconsistent relation; callers must deny rather than infer a replacement.
- **Service ownership:** `prepare_to_start()` persists/loads the current deployment policy record B, reads the durable creation revision A, and rejects if their immutable IDs differ. It must make that comparison before `quota_is_current()`, `_advance()`, the workflow, provider, sandbox, or SSE publisher.
- **API/lifecycle ownership:** Keep the existing FastAPI lifespan as the source of the deployment policy and the existing job route as the safe projection boundary. A rejected queued cursor exposes a sanitized policy-transition reason only; it never receives policy IDs, fingerprints, quotas, or an automatic reauthorization. A caller must submit a new server-authorized job under B.
