## PLAN-02 Closure Trace

### Run-bound review, apply, and replay

`PlaybookInspector` owns `runIdRef`, `transitionRef`, and rendered
`transitionId` at
`frontend/src/components/decision/PlaybookInspector.tsx:288-297`.

Every generated or manually selected run enters through `transitionToRun`:

- it synchronously advances the transition epoch;
- writes the new run ID into the ref;
- updates the selected run/cutoff;
- resets review, apply, and replay mutation observers.

See `PlaybookInspector.tsx:303-310,360-378`.

Review, apply, and replay mutations capture `{runId, transitionId}` rather than
closing over mutable selection state
(`PlaybookInspector.tsx:311-357`). Review and apply cache writes reject late
results unless both values still match the current refs
(`PlaybookInspector.tsx:314-320,340-345`).

At display time, `mutationMatchesRun` gates every review/apply/replay
data/error/pending value before it reaches `PlaybookDetails`
(`PlaybookInspector.tsx:471-508`). A response from run A therefore cannot appear
under run B even if it settles after the transition.

The delayed-settlement browser case starts review and replay for run A, selects
run B, releases both run-A responses, and proves neither old review state nor
old replay evidence renders under B
(`frontend/e2e/decision-playbook-flow.spec.ts:215-312`).

### Complete per-field adjustment audit

The server applies or rejects each supplied field independently and persists one
audit record per field
(`backend/app/decision/adjustments.py:59-97`). The former grouped
`auditFor(...).find(...)` path is gone. The UI maps every
`run.adjustments` item to an independently labeled row and retains disposition,
rationale, proposed value, and final value
(`PlaybookInspector.tsx:217-244`).

The happy-path browser fixture proposes both `entry_low` and `entry_high`,
returns distinct `applied` and `clamped` audit rows, and asserts both rows and
values remain visible
(`decision-playbook-flow.spec.ts:107-150,181-205`).

### Replay failure and retry

Replay variables include the selected run ID, cutoff, and transition epoch
(`PlaybookInspector.tsx:348-357,475-488`). A matching replay error now renders
an accessible alert and retry button while preserving the cutoff
(`PlaybookInspector.tsx:245-284`).

The fail-then-retry browser case verifies:

- the 503 response produces visible feedback;
- cutoff `2026-07-20` remains in the input;
- retry succeeds;
- both POST bodies contain the same run ID and cutoff.

See `decision-playbook-flow.spec.ts:314-376`.

### Complete decision flow

`decision-playbook-flow.spec.ts:72-213` traces the complete user path:

1. generate `{symbol, as_of}` and display the server run ID;
2. request AI review and display its still-unapplied two-field proposal;
3. prove no adjustment request occurred before explicit confirmation;
4. click “应用受限调整”;
5. assert the exact two-field POST payload;
6. render changed final values beside the deterministic baseline;
7. render both distinct audit dispositions;
8. replay with `{run_ids, as_of}`;
9. display the provider-free replay result.

The backend adjustment data-flow trace reaches
`DecisionAdjustmentService.apply` → `record_adjustment_audit` /
`replace_decision_final` → persisted response. The replay trace resolves
persisted runs, reads governed historical rows, passes the AI replay guard, and
persists the provider-free replay record.
